# Сбор цен по проекту

## Вход и зависимость

Прочитай AGENTS.md и относящиеся к товарам документы текущего проекта. Возьми из них модели, комплектацию и заданные ссылки; учти уточнения пользователя. Если товар не определён, запроси его название.

Открой и используй скилл `extract-price` из доступного каталога навыков. Если он не указан в каталоге, проверь `extract-price/SKILL.md` в текущем проекте. Если зависимость недоступна, сообщи об этом и остановись. Правила выбора сайтов, чтения страниц, извлечения, нормализации и проверки полей определяет только `extract-price`; здесь они не переопределяются.

## Прогон

1. Составь список товаров и URL из запроса и проекта. Если сайты не заданы, возьми базовые URL из `extract-price`. Для неподдерживаемых сайтов укажи ограничение зависимости, сохрани их в отчёте как необработанные.
2. Для каждого товара используй `extract-price`, передав URL и контекст модели и комплектации. При базовом URL поиск карточки выполняй по его инструкциям. Это применение навыка агентом, а не требование отдельного инструмента или запуска другого агента.
3. Включай в сравнение только подтверждённую целевую комплектацию. Например, если проект требует зарядное устройство и аккумуляторы, предложение одного снегоуборщика не подходит. Если состав не подтверждён, отметь причину пропуска; не подставляй цену другого комплекта и не складывай цены отдельных товаров.
4. Успешный JSON зависимости используй как результат одной строки. Сохрани фактический URL проверенной карточки из контекста её открытия: JSON зависимости содержит только три поля. Повторяющиеся ссылки на одно и то же предложение объедини.
5. После ошибки отдельного URL продолжи остальные независимые проверки. Для недоступной страницы, отсутствующего товара или неподтверждённых данных сохрани строку с исходным либо проверенным URL и прочерками в трёх полях; рядом с таблицей объясни причину для этой ссылки. Прочерк означает отсутствие достоверного результата, а не значение поля.

## Таблица прогона

Выведи дату и время проверки с часовым поясом и название товара с требуемой комплектацией. Для нескольких товаров сформируй отдельные таблицы с названиями товаров над ними.

В каждой таблице ровно четыре столбца в следующем порядке:

| URL | regular_price | sale_price | has_credit |
| --- | --- | --- | --- |

Каждый обработанный URL должен быть представлен результатом или строкой с причиной пропуска. В URL используй кликабельную ссылку. В успешных строках переноси значения JSON без изменений; определения и допустимые значения полей берутся из `extract-price`. Валюту и существенные условия предложения укажи рядом с таблицей, сохраняя заданный набор столбцов.

Требование `extract-price` вернуть только JSON относится к результату извлечения одной карточки; итог `tracker` — общая таблица и сохранённая выгрузка. Если успешных результатов нет, сообщи об этом явно и сохрани сведения о неудачном прогоне.

## Ежедневная выгрузка

Храни все прогоны в [igorshpindler-tech/tracker-data](https://github.com/igorshpindler-tech/tracker-data). Точка после `tracker-data` в исходной ссылке пользователя — знак препинания, а не часть имени репозитория.

Используй один файл `YYYY-MM-DD.json` в корне репозитория на календарный день начала прогона. Дату определяй в часовом поясе проекта, а при его отсутствии — пользователя; для текущего проекта это `Europe/Moscow`. Несколько запусков в один день добавляй в массив `runs` этого файла, сохраняя предыдущие прогоны и файлы других дней. Ежедневный формат хранения сам по себе не создаёт расписание запусков.

Для нового файла используй JSON-объект с полями `date` (дата из имени файла), `timezone` (имя часового пояса) и `runs` (массив прогонов). Каждый прогон содержит:

- `run_id`: уникальный идентификатор, сохраняемый при повторной попытке публикации этого прогона;
- `started_at`, `finished_at`: время начала и окончания сбора в ISO 8601 со смещением часового пояса;
- `results`: массив всех проверенных сочетаний товара и URL.

Каждая запись `results` содержит `product` (модель), `configuration` (требуемый комплект), `url`, `checked_at`, `currency`, `status`, `regular_price`, `sale_price`, `has_credit` и `error`. Для успешной записи `status` равен `ok`, три поля извлечения переноси без изменения из результата `extract-price`, `error` равен `null`; валюту записывай по проверенному предложению. Для неудачной проверки `status` равен `error`, три поля извлечения равны `null`, а `error` содержит причину. Неизвестную валюту записывай как `null`. Эти `null` обозначают ошибку только вместе со статусом `error` и не являются успешным объектом `extract-price`.

## Сохранение в GitHub

Перед записью проверь доступ к указанному репозиторию, его основную ветку, инструкции и существующий файл дня через доступный GitHub-инструмент либо авторизованный GitHub CLI/Git. Сохраняй в основной ветке; её имя получи из репозитория. Для существующего файла прочитай текущий JSON и добавь новый прогон с сохранением прежних данных. Если структура несовместима, сохрани локальную выгрузку и сообщи о конфликте формата вместо перезаписи истории.

Запиши локальную копию в рабочую папку проекта и проверь корректность JSON, соответствие даты имени файла, типов полей и полноту результатов. Затем создай или обнови только файл дня в `igorshpindler-tech/tracker-data`. Обновление выполняй с проверкой текущей версии файла или коммита. При конфликте перечитай файл, объедини прогоны по `run_id` и повтори запись один раз; повторная публикация того же `run_id` не должна добавлять дубликат. При сохранении через Git включай в коммит только целевой файл дня.

При отсутствии доступа, ошибке публикации или повторном конфликте сохрани локальный файл и сообщи причину и путь к нему. После успешной записи прочитай удалённый файл и подтверди наличие текущего `run_id`. В ответе покажи таблицу и ссылку на файл дня в GitHub; если удалённое сохранение не подтверждено, явно укажи это. Прогон полностью завершён, когда все запланированные проверки отражены в результатах и выгрузка подтверждена в репозитории.
